QA Process Flow

Module development → tests → QA agents → defect lifecycle
← Back to viewer

This is the baseline standard process for how a Vibrantix module moves from development through test authoring, QA agent validation, defect logging, and defect resolution. For the full written procedure (cadence table, onboarding checklist, field conventions), see PROCESS.md in the repo root.

Source of truth for defects going forward: new defects are written directly into the AI Defects Management System — not into QA_Tracker/*.md, which stays frozen as historical record.

Developer QA Agent QA Tester / SDET Release Manager
  1. 1

    Module development

    Developer implements or changes a feature in the module's actual code (vibrantix-backend, vibrantix-client-panel, or the relevant microservice). No test-management-system involvement yet.

  2. 2

    Developer authors test cases

    In the same PR as the code change, the developer adds/updates test cases covering what they built — status starts draft until reviewed. Minimum bar: one test case per new user-facing behavior or bug fixed.

    → Modules system
New module? Register its slug (scripts/seed-modules.js + scripts/seed-defects.js) and provision a dedicated QA agent once there's real code and a baseline of tests to validate against — see the onboarding checklist in PROCESS.md. Existing modules already have their agent; only update it when the module changes materially.
  1. 3

    QA agent provisioning / maintenance

    The module's dedicated QA agent (e.g. Evidence_Management_QA_Agent) exists and is kept current — updated when real code paths change materially, or when a recurring defect class isn't yet being caught. Lower-frequency than every PR.

  2. 4

    QA agent run

    The agent reads the real source code, the module's existing test cases (to find coverage gaps), and its existing open defects (to avoid duplicates and to re-verify previous findings). It produces two outputs:

    • Gap-fill test cases — new cases, status: draft, owner: QA, reviewed same as developer-authored ones (Stage 5).

    • Defects — real findings with concrete file/line detail, severity, and status: open.

    → Modules system → AI Defects Management System
  3. 5

    QA tester review, promotion & automation

    1. Review draft test cases (developer- or agent-authored) — promote to active, or deprecated if wrong/redundant.

    2. Automate promoted cases — write the real spec, set automationStatus and a verified automationRef.

    3. Execute runs — Mark Pass/Fail/Blocked/Skipped in the viewer, on whatever cadence applies.

    → Modules system
  4. 6

    Defect triage

    Critical — fix immediately, blocks release. High — fix before next release. Medium / Low — scheduled normally. Set status: in_progress once picked up.

  5. 7

    Fix and re-verify

    Developer fixes the defect; developer or QA tester sets status: fixed with a statusRaw note referencing the fix (e.g. "Fixed in PR #482") via the viewer's Status editor.

    On the module's next QA agent run, the agent specifically re-checks: genuinely fixed → stays fixed; reintroduced → flips to regressed; can't verify → cannot_verify.

    Regressed defects loop back to Stage 6 — triage again
  6. 8

    Release gate

    Before a release, filter the Defects system by Critical/High severity and an open-ish status. Export the filtered view as the sign-off artifact. Anything on that list gets fixed first or is explicitly accepted as known risk — never silently shipped.

Cadence & triggers

StepTrigger
Developer test authoringEvery PR that changes module behavior
QA agent maintenanceWhen the module changes materially, or a recurring defect class isn't caught
QA agent runOn-demand before a release, or a scheduled cadence per module
Test review / promotion / automationAs draft cases accumulate — don't let them pile up unreviewed
Defect triageContinuous — as soon as new defects land
Re-verificationEvery subsequent QA agent run for that module
Release gateBefore every release
