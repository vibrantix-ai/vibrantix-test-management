# Vibrantix Test Management System

A modular, file-based test case repository for the Vibrantix GRC platform, rendered by a
static HTML viewer with filtering and Excel/CSV export — for SDET review, automation
planning, and release testing sign-off.

There is no database and no build step. Test cases live as plain JSON files, one file per
entity per test category, so they stay easy to diff in git, easy to hand to Claude as scoped
context, and easy for multiple people to edit without merge conflicts.

**Looking for the end-to-end QA workflow** — how a module goes from development, through
developer-authored tests, QA agent validation, and defect logging, to a fixed/verified defect?
See [PROCESS.md](PROCESS.md). This README and [SCHEMA.md](SCHEMA.md) describe the *shape* of
the data; PROCESS.md describes *who does what, when*.

## Six systems, one architecture

The repository is organized into 6 sibling **systems**, each covering a different axis of the
platform, all following the identical directory/manifest/`_meta.json` shape described below:

| System | Entity | Covers |
|---|---|---|
| **Modules** | Module | Per-module functional test suites (Evidence Management, Risk Register, ...) — the original system |
| **Frameworks** | Framework | Compliance framework requirements + UCL (shared control layer) mapping correctness |
| **Logs** | Log Source | Correctness of logs generated by each module |
| **Audit Reports** | Framework Audit Report | Report field accuracy for each compliance framework's generated audit report |
| **Integrations** | Connector | Connector connection flows and per-connector checks |
| **AI Defects Management** | Module | Real defects converted from `QA_Tracker/` live defect trackers — severity + status lifecycle, status editable |

The viewer's top nav switches between systems. `data/manifest.json` is the index that lists
all 6 — see [SCHEMA.md](SCHEMA.md) for the full shape.

**Current content status:** Modules has ~1185 real test cases. The AI Defects Management
system has ~434 real defects (see "The Defects system" below). The other 4 systems
(Frameworks, Logs, Audit Reports, Integrations) currently have only entity scaffolding
(`manifest.json` + `_meta.json` per entity, no category files) — actual test-case content for
them is a later phase, added the same way Modules' content was: by delegating to the relevant
QA agent or SDET with real code context.

## The Defects system

Unlike the other 5 systems, **AI Defects Management** holds a genuinely different record shape
— a *defect* (severity, status lifecycle, narrative, fix evidence), not a *test case* (steps,
expected result, automation status). Its records are real data converted from
`QA_Tracker/`'s markdown live-defect trackers and one CSV bug list — `QA_Tracker/` itself is
left untouched as the historical source; conversion only reads from it.

- **Schema**: `schema/defect.schema.json` (sibling to `schema/test-case.schema.json`).
- **Category axis**: severity (`critical`/`high`/`medium`/`low`) instead of the 9 QA
  categories — a defect isn't a unit/e2e/etc. test, but it does have a severity, so
  `data/defects/<slug>/critical.json` etc. reuses the same per-file-per-bucket plumbing.
- **Entities**: the same 13 module slugs that already exist in the Modules registry
  (`evidence-management`, `grc-framework`, `policy-management`, `trust-vault`,
  `vendor-management`, `notifications`, `tasks`, `audit-assurance`, `risk-register`,
  `security-vulnerability`, `rbac-security`, `tenant-isolation`, `cloud-posture`) — zero new
  slugs invented.
- **Status is editable, nothing else is** — the detail panel has a Status dropdown (+
  optional status-note text field) that writes straight back to the source JSON via
  `PUT /api/defect`, the same on-disk-write pattern as the test-case systems' Mark Pass/Fail.
  There's no Pass/Fail marking and no Automation panel — those concepts don't apply to a
  defect. Saving a status change auto-stamps `lastVerified` to today, mirroring how the
  test-case endpoint auto-bumps `updatedAt`.
- **What was converted, and what wasn't**: see "Defects conversion scope" below.

Full field reference and the exact source-column mapping per tracker variant are in
[SCHEMA.md](SCHEMA.md).

## Quick start

```bash
node server.js        # or: npm start
# open http://localhost:4500
```

A server is required (not `file://`) because the viewer `fetch()`s local JSON files, which
browsers block under CORS from the filesystem. `server.js` has zero dependencies — just Node.

## Categories

`unit`, `integration`, `e2e`, `security`, `smoke`, `sanity`, `regression`, `performance`,
`accessibility` — the same 9 categories apply across the 5 test-case-shaped systems
(Modules/Frameworks/Logs/Audit Reports/Integrations), each defined in that system's own
`data/<system>/manifest.json`. All are filterable in the viewer and become separate tabs in the
Excel export. An entity doesn't need every category; only create the files that have real
content. The **Defects** system uses a different 4-value axis instead — `critical`/`high`/
`medium`/`low` (severity) — see "The Defects system" above.

## The viewer

- **System tabs** at the top switch between the 6 systems, and each system has its own
  bookmarkable/shareable URL — `/app/modules`, `/app/frameworks`, `/app/logs`,
  `/app/audit-reports`, `/app/integrations`, `/app/defects`. Navigating directly to one of these
  (or using browser back/forward) loads that system immediately; `/app/` alone resolves to the
  first system in the manifest. This is plain client-side routing (`app.js` reads/writes the URL
  via `history.pushState`) — `server.js` just serves `index.html` for any `/app/<slug>` path that
  isn't a real file, same idea as any single-page app's server fallback. Switching reloads that
  system's entities and records and resets filters (entity slugs and filter facets aren't
  comparable across systems). The Defects system renders a genuinely different UI (see below) — everything
  else in this section describes the 5 test-case-shaped systems.
- Faceted filters: category, priority, type (manual/automated/both), automation status, status,
  **result** (pass/fail/blocked/skipped/not run), the current system's entity (labelled
  Module/Framework/Log Source/Framework Audit Report/Connector), tags, and free-text search
  across title/steps/expected result/tags.
- Click a row to open the full test case (preconditions, steps, expected result, traceability).
- **Mark a result** — from the detail panel, click Pass/Fail/Blocked/Skipped (or reset to not
  run), optionally add your name and notes, and it's written straight back to the source JSON
  file on disk. Same panel lets you correct the `automationStatus`/`automationRef` fields by
  hand. This requires running via `node server.js` (below) — it's a real write API, not just a
  static viewer. See "Marking results" in [SCHEMA.md](SCHEMA.md) for details and an important
  caveat about trusting existing `automationRef` values.
- **Export to Excel** — writes an `.xlsx` with an "All Test Cases" sheet plus one sheet per
  category present in the current filtered view, respecting whatever filters are active, and
  including each case's latest Result/Run At/Run By/Notes.
- **Export CSV** — same filtered rows, single flat file, for quick diffing or import into other
  tools.

Exports always reflect the *current filters* — filter down to `module=evidence-management,
category=e2e, status=active` before exporting to hand a release-testing team exactly their
scope.

**In the Defects system**, the filter panel instead shows Severity (reusing the Category chip
slot) and Status (reusing the Result chip slot; Priority/Type/Automation/lifecycle-Status are
hidden — they have no defect equivalent). The table shows ID/Module/Severity/Category/Title/
Status, and the detail panel shows the narrative/requirement/tags/affected files/fix evidence/
timeline/source plus a **Status** editor (dropdown + optional note, "Save status" button) —
there's no Pass/Fail marking and no Automation panel, since a defect isn't something you "run"
or automate, but its status (open/fixed/regressed/...) is exactly the kind of thing that
changes as you re-verify it, so that one field is writable. Export column sets and filenames
adjust accordingly (`vibrantix-defects-<date>.xlsx`/`.csv`).

## Adding or updating test cases

1. Read [SCHEMA.md](SCHEMA.md) for the field reference and an example object.
2. Open (or create) `data/<system>/<slug>/<category>.json` — it's a plain JSON array of test
   case objects (e.g. `data/frameworks/iso-27001/e2e.json`, `data/modules/evidence-management/e2e.json`).
3. Follow the ID convention already used for that entity (`<PREFIX>-<CATEGORY-CODE>-<seq>`).
   Never renumber a published ID; set `status: "deprecated"` instead of deleting.
4. Refresh the viewer (it re-fetches on every load, no cache to bust).

### Adding a brand-new entity to an existing system

1. Add an entry to that system's seed script (e.g. `FRAMEWORKS` in `scripts/seed-frameworks.js`,
   `CONNECTORS` in `scripts/seed-integrations.js`) and run its `npm run seed:<system>` script —
   it creates the folder, `_meta.json`, and updates that system's `manifest.json` without
   touching any existing test data.
2. Add category files as needed.

### Adding a brand-new system

1. Add an entry to `SYSTEMS` in `scripts/seed-systems.js` (slug, name, entityLabel, dataDir,
   description) and run `npm run seed:systems`.
2. Write a new `scripts/seed-<system>.js` mirroring the pattern in the existing ones — writes
   `data/<dataDir>/manifest.json` + one `_meta.json` per entity.
3. `server.js`'s `SYSTEM_DATA_DIRS` map and the viewer's `app.js` are already system-generic —
   no code changes needed beyond registering the new system slug/dataDir there too.

### Using Claude to find gaps or write new cases

Because each `<system>/<slug>/<category>.json` file is small and self-contained, paste the
relevant file(s) plus a description of the current feature behavior and ask Claude to identify
missing coverage or draft new cases in the same schema. See the "Using this with Claude" section
at the bottom of [SCHEMA.md](SCHEMA.md) for the recommended framing.

behavior rather than drifting into speculation.

## Defects conversion scope

The AI Defects Management system was populated by converting real content out of
`QA_Tracker/` (its own nested git repo) — not scaffolded, not generated. What got converted,
and what was deliberately left alone:

**Converted (~434 defects, 13 sources):**
- 11 markdown `*_QA_LIVE_TRACKER.md` live-defect registries — Evidence Management (44,
  including 6 cross-service defects), GRC Framework (21), Policy Management (56), Trust Vault
  (33), Vendor Management (25), Notifications (15), Tasks (24), Audit Assurance (58, mixed
  CD-/D-/H-/M- ID prefixes — all assigned `module: "audit-assurance"`, original IDs preserved
  unchanged), Risk Register (39, alternate column schema), Security Vulnerability (47,
  alternate column schema with CWE/OWASP), RBAC/Security (25, from `QA_Tracker/RBAC/`).
- `QA_Tracker/TENANT_ISOLATION/TENANT_ISOLATION_QA_LIVE_TRACKER.md` (25, same alternate schema
  as Risk Register).
- `QA_Tracker/CLOUD_POSTURE_BUGS_FOUND.csv` (22 — no native IDs, synthesized `CP-NNN`; no
  OPEN/FIXED lifecycle, `status` defaulted to `"open"` for every row, with the source's
  one-time `Verified` confirmation flag kept separately as `verified`).

**Explicitly excluded, left untouched in `QA_Tracker/`** (confirmed not defect registries by
reading each, not assumed): `QA_AGENT_COVERAGE_ANALYSIS.md` (coverage proposal doc), and under
`QA_Tracker/RBAC/`: `RBAC_ARCHITECTURE_ANALYSIS.md`, `RBAC_GAP_ANALYSIS.md`,
`RBAC_PERMISSION_MATRIX.md`, `RBAC_AUTOMATED_TEST_PLAN.md`, `PLAYWRIGHT_RBAC_TESTS.md`,
`API_SECURITY_TEST_SUITE.md`, `API_AUTHORIZATION_AUDIT.md`, `CLIENT_PANEL_RBAC_AUDIT.md`,
`BROKEN_ACCESS_CONTROL_FINDINGS.md`, `MICROSERVICE_SECURITY_AUDIT.md` — these are prose,
test-plan, or one-time-finding documents with no OPEN/FIXED status lifecycle.
`QA_Tracker/CLOUD_POSTURE_USE_CASE_ANALYSIS.csv` is a feature-coverage matrix, not a bug list —
excluded. The `.pdf` files are 1:1 md-to-pdf renders (via `qa-tracker.css`) of a same-named
`.md` — excluded as redundant. `AUDIT_ASSURANCE_QA_LIVE_TRACKER1.pdf` is an orphan with no
`.md` sibling — left alone, a known gap, not investigated further.

**Known content gap:** `security-vulnerability`'s defects omit the richer narrative from that
tracker's "1B) Defect Detail Cards" section (the converting agent judged its extra fields —
Exploit Narrative, Business Impact, Fix Guidance — didn't map cleanly and left `description`
unpopulated for all 47 rather than guess a mapping). Every other converted module has
`description` populated from its tracker's detail-card narrative where one exists. Revisit this
file specifically if the fuller narrative is wanted later.

To convert a 14th source later, follow the same pattern: read the tracker in full, map its
columns to `schema/defect.schema.json`'s fields (see per-variant mapping rules in
[SCHEMA.md](SCHEMA.md)), write `data/defects/<slug>/<severity>.json`, then add the entity to
`MODULES` in `scripts/seed-defects.js` and run `npm run seed:defects` to register it in the
manifest/`_meta.json` (that script never touches the severity-bucket content files).
